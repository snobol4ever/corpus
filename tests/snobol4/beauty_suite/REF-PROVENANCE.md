## The situation

Three drivers **match their pinned `.ref` exactly** while the **live SPITBOL oracle refuses to run them at all**:

| driver | live `sbl -bf` says | site |
|---|---|---|
| `tree_driver` | `ERROR 067 -- array dimension is zero, negative or out of range` | `tree.sno:16` |
| `trace_driver` | `ERROR 243 -- function result in nreturn is not name` | line 59 |
| `ReadWrite_driver` | `ERROR 116 -- inappropriate file specification for input` | `ReadWrite.sno:9` |

All three reproduce on demand (re-verified 2026-08-29 against `/home/resources/x64/bin/sbl -bf`). In every case
**SCRIP runs FURTHER than the live oracle** and produces the pinned answer.

## 1. Provenance — established from git receipts, not inferred

`git log --follow` on each `.ref` terminates at the same commit:

```

```

⭐ **Every commit after the first is a RENAME. All three files are BYTE-IDENTICAL to their 2026-03-29 import**
(verified by `git show 04d21dc42:<path> | cmp`).

⛔ **So the answer to "which engine produced these pins" is: none of ours.** They were **inherited wholesale from the
`one4all` repository** and have never been regenerated by any oracle in this project. They do not merely predate the
current grading regime — they predate the practice of pinning against an oracle here at all. This is a stronger
finding than the s191 `prototype-array-dim` case it was filed alongside: that was one `.ref` pinned to CSNOBOL4
*instead of* SPITBOL; these three were never pinned to an engine we grade against.

## 2. Adjudication — all three are (a) genuine SPITBOL restrictions, not (b) sbl-side limitations

Each code is in the SPITBOL v3.7 manual's own documented error table:

| code | manual line | text |
|---|---|---|
| 067 | 11380 | `ARRAY dimension is zero,negative or out of range` |
| 243 | 11572 | `Function result in NRETURN is not name` |
| 116 | 11434 | `Inappropriate file specification for INPUT` |

⛔ **None is an sbl implementation artifact.** The live oracle is enforcing documented SPITBOL semantics, and the
programs violate them. ⭐ **The consequence is the uncomfortable half: SCRIP is MORE PERMISSIVE than SPITBOL on these
three constructs, and the pinned `.ref` records that permissiveness as the expected answer.** The pin is not
"correct output from a different engine" — it is output SPITBOL says should never have been produced.

## 3. Why nothing was changed

- ⛔ **Re-pinning is a corpus-contract precedent, not a seat's call** — moving a pin *away* from an oracle is
  precisely the decision the row escalates. 17/17 M1 DOD currently depends on these pins.
- ⛔ **"Curing" SCRIP to match live sbl is equally out of scope** and would be a semantic narrowing, not a bug fix.
- ⭐ **The third option nobody has named** and which the evidence now makes available: mark the three
  **out-of-dialect** — the programs use constructs SPITBOL rejects, so they are not SNOBOL4-conformance witnesses at
  all, whatever they are useful for. That is a different disposition from re-pinning and does not touch a `.ref`.
